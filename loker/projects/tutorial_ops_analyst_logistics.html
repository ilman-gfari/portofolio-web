Deskripsi

The Operations Analyst (Data & Automation) is the Logistics team's in-house builder of data tools and automation: ETL flows, dashboards and reports, data-entry tools for scattered operational data, and AI-assisted workflows. They also support the Business Analyst with requirement gathering, SOP documentation and reporting.

  • Build and maintain ETL flows with deterministic, verifiable output, reconciled against source data.
  • Build internal web tools to capture operational data not available via API, with input validation and audit trails.
  • Design and maintain database schemas using constraints and validation (no duplicates, no orphaned records).
  • Build dashboards and reports on top of the existing data platform.
  • Build AI-assisted workflows where they fit, with checks on the AI's output.
  • Write tests from known-input and expected-output cases agreed with the requester.
  • Reuse and extend existing live tools as templates; document each tool shipped.
  • Use AI coding tools daily and be able to explain any code shipped.
  • Work with Logistics team members, collect feedback after each launch, improve tools.
  • Support requirement gathering, SOP documentation, and ad hoc reporting.

Kualifikasi

  • S1 Computer Science, Information Systems, Data, atau terkait; 0–2 tahun pengalaman; fresh graduate diterima bila punya internship, freelance, atau part-time yang relevan.
  • Pernah membangun minimal satu proyek end-to-end yang dipakai orang lain.
  • Pengalaman dengan AI coding assistant dan kemampuan menilai hasilnya.
  • Python dan SQL (baca, tulis, debug mandiri); dasar database relasional (desain tabel, PK/FK, constraint, join, index, transaksi) di PostgreSQL/MySQL/SQL Server.
  • Git dan automated testing dasar.
  • Komunikasi tertulis jelas, nyaman menerima kebutuhan dari rekan non-teknis, minat pada operasi logistik, bisa bekerja dari kantor bila diperlukan.

Lo nggak perlu jadi ahli logistik, tapi harus paham bahasa dan masalah sehari-harinya.

Masalah data yang hampir pasti ada di operasi logistik

Data tersebar

Spreadsheet per tim, WhatsApp, email dari carrier, portal tanpa API. Tool input data ada karena ini.

Format tidak seragam

Kode carrier, tanggal, nama kota, dan satuan berbeda-beda antar sumber.

Duplikasi & data yatim

Nomor resi ganda, kendala tanpa pengiriman induk, pengiriman tanpa carrier valid.

Catatan bebas

Kolom "keterangan" berisi teks acak ("barang basah", "alamat gak ketemu"), yang sulit dianalisis tanpa pengelompokan.

Definisi berbeda

"Terlambat" menurut gudang bisa beda dengan menurut carrier atau finance.

Proses berubah cepat

Tool harus mudah diubah dan didokumentasikan karena prosesnya sering berubah.

Cara belajar cepat Baca 2–3 artikel dasar tentang supply chain dan last-mile delivery, lalu coba "bayangkan satu paket" dari gudang sampai diterima dan tulis di titik mana data dicatat dan oleh siapa. Latihan itu otomatis menunjukkan di mana data bisa salah. Di interview, ceritakan latihan tersebut, jauh lebih meyakinkan daripada "saya tertarik logistik".

Cara menggali kebutuhan dari rekan non-teknis

Poin penting di lowongan: "comfortable taking requirements from non-technical colleagues." Gunakan pertanyaan seperti ini:

  • "Hari ini lo ngerjain ini gimana? Bisa tunjukin langsung?" (amati prosesnya, jangan hanya dengar ceritanya)
  • "Datanya datang dari mana, siapa yang update, seberapa sering?"
  • "Kalau datanya salah, apa dampaknya dan siapa yang tahu duluan?"
  • "Hasilnya dipakai siapa untuk keputusan apa?"
  • "Apa definisi 'terlambat' / 'selesai' / 'rusak' di tim lo? Ada contoh kasus perbatasan?"
  • "Seperti apa hasil yang bikin lo bilang 'ini berhasil'?" (jadi acceptance criteria)

1. Form menolak nomor resi yang tidak ada di data pengiriman.
2. Kategori kendala dipilih dari daftar baku (tidak boleh teks bebas).
3. Kendala yang sama (resi + kategori) tidak bisa dicatat dua kali selama masih OPEN.
4. Setiap pembuatan/perubahan tercatat: siapa, kapan, nilai sebelum dan sesudah.
5. Laporan mingguan menampilkan jumlah kendala per carrier dan kategori.

3Mock Project: Shipment Exception Tracker

Satu proyek yang mencakup hampir semua poin lowongan: ETL, schema, web tool, dashboard, workflow AI, tes, dan dokumentasi.

Skenario Tim Logistik (ilustrasi) menerima data pengiriman dari beberapa carrier lewat file CSV/Excel dengan format berbeda-beda. Kendala pengiriman (rusak, terlambat, hilang, alamat salah) saat ini dicatat di spreadsheet dan chat, tanpa validasi. Akibatnya laporan mingguan sering berbeda antar orang, nomor resi ganda, dan kendala yang "hilang". Kebutuhan: (1) ETL yang membersihkan data carrier dan terbukti cocok dengan sumber, (2) web tool untuk mencatat kendala dengan validasi dan jejak audit, (3) database yang menjaga kebersihan data, (4) dashboard performa carrier, (5) pengelompokan catatan bebas dengan bantuan AI yang aman.

Arsitektur sederhana

File carrier (CSV/Excel)→ ETL: bersihkan, tolak, rekonsiliasi→ PostgreSQL (constraint + audit log)→ Dashboard / laporan
Form web (FastAPI)→ Validasi input→ PostgreSQL→ Klasifikasi catatan (AI + guardrail)

Langkah 1 — Rancang schema (constraint adalah garis pertahanan pertama)

-- schema.sql (PostgreSQL)
CREATE TABLE carrier (
  carrier_id   SERIAL PRIMARY KEY,
  carrier_code TEXT NOT NULL UNIQUE,
  carrier_name TEXT NOT NULL
);

CREATE TABLE shipment (
  shipment_id    BIGSERIAL PRIMARY KEY,
  shipment_ref   TEXT NOT NULL UNIQUE,                       -- cegah resi ganda
  carrier_id     INT  NOT NULL REFERENCES carrier(carrier_id),-- cegah carrier tak dikenal
  origin         TEXT NOT NULL,
  destination    TEXT NOT NULL,
  ship_date      DATE NOT NULL,
  promised_date  DATE NOT NULL,
  delivered_date DATE,
  weight_kg      NUMERIC(10,2) NOT NULL CHECK (weight_kg > 0),
  freight_cost   NUMERIC(14,2) NOT NULL CHECK (freight_cost >= 0),
  CHECK (promised_date >= ship_date),
  CHECK (delivered_date IS NULL OR delivered_date >= ship_date)
);
CREATE INDEX ix_shipment_carrier_date ON shipment (carrier_id, ship_date);

CREATE TABLE delivery_exception (
  exception_id BIGSERIAL PRIMARY KEY,
  shipment_id  BIGINT NOT NULL REFERENCES shipment(shipment_id) ON DELETE RESTRICT, -- cegah data yatim
  category     TEXT NOT NULL CHECK (category IN
               ('DAMAGED','DELAYED','LOST','WRONG_ADDRESS','REFUSED','OTHER')),
  status       TEXT NOT NULL DEFAULT 'OPEN' CHECK (status IN ('OPEN','RESOLVED')),
  note         TEXT,
  reported_by  TEXT NOT NULL,
  reported_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- satu kendala OPEN per resi + kategori (kendala sudah RESOLVED boleh muncul lagi)
CREATE UNIQUE INDEX ux_open_exception ON delivery_exception (shipment_id, category)
  WHERE status = 'OPEN';

CREATE TABLE audit_log (
  audit_id   BIGSERIAL PRIMARY KEY,
  table_name TEXT NOT NULL,
  record_id  BIGINT NOT NULL,
  action     TEXT NOT NULL CHECK (action IN ('INSERT','UPDATE')),
  changed_by TEXT NOT NULL,
  changed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  old_data   JSONB,
  new_data   JSONB
);

CREATE FUNCTION log_exception_change() RETURNS trigger AS $$
BEGIN
  INSERT INTO audit_log (table_name, record_id, action, changed_by, old_data, new_data)
  VALUES ('delivery_exception', NEW.exception_id, TG_OP,
          COALESCE(current_setting('app.user', true), 'unknown'),
          CASE WHEN TG_OP = 'UPDATE' THEN to_jsonb(OLD) END,
          to_jsonb(NEW));
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_exception_audit
AFTER INSERT OR UPDATE ON delivery_exception
FOR EACH ROW EXECUTE FUNCTION log_exception_change();
Cara menjelaskannya di interview "Validasi di aplikasi bisa dilewati (skrip lain, import manual). Constraint di database nggak bisa. Jadi saya taruh aturan inti di sana: PRIMARY KEY dan UNIQUE untuk mencegah duplikat, FOREIGN KEY untuk mencegah data yatim, CHECK untuk nilai yang masuk akal, dan partial unique index untuk aturan 'satu kendala OPEN per resi dan kategori'. Delete sengaja tidak dipakai; yang ada hanya status RESOLVED, supaya jejaknya tidak hilang."

Langkah 2 — ETL yang deterministik dan bisa direkonsiliasi

Prinsip: input sama → output sama (tidak ada angka acak, urutan diurutkan eksplisit), tidak ada baris yang hilang diam-diam (setiap baris masuk ke clean atau rejects dengan alasan), dan ada pengecekan jumlah.

# etl.py
import pandas as pd

TEXT_COLS = ["shipment_ref", "carrier_code", "origin", "destination"]
DATE_COLS = ["ship_date", "promised_date", "delivered_date"]

def transform(raw: pd.DataFrame):
    df = raw.copy()
    df.columns = [c.strip().lower() for c in df.columns]

    for c in TEXT_COLS:
        df[c] = df[c].astype("string").str.strip()
    df["shipment_ref"] = df["shipment_ref"].str.upper()
    df["carrier_code"] = df["carrier_code"].str.upper()

    for c in DATE_COLS:   # format eksplisit: tidak menebak (menghindari ambiguitas 03/04)
        df[c] = pd.to_datetime(df[c], format="%Y-%m-%d", errors="coerce")
    df["weight_kg"]    = pd.to_numeric(df["weight_kg"], errors="coerce")
    df["freight_cost"] = pd.to_numeric(df["freight_cost"], errors="coerce")

    # aturan validasi: alasan penolakan pertama yang cocok yang dipakai
    rules = [
        ("MISSING_REF",       (df["shipment_ref"].isna() | (df["shipment_ref"] == "")).fillna(True)),
        ("BAD_SHIP_DATE",     df["ship_date"].isna()),
        ("BAD_PROMISED_DATE", df["promised_date"].isna() | (df["promised_date"] < df["ship_date"])),
        ("INVALID_WEIGHT",    ~(df["weight_kg"] > 0)),
        ("INVALID_COST",      ~(df["freight_cost"] >= 0)),
    ]
    reason = pd.Series("", index=df.index)
    for name, mask in rules:
        reason = reason.mask((reason == "") & mask, name)

    rejects = df[reason != ""].assign(reject_reason=reason[reason != ""])
    ok = df[reason == ""].sort_values(
        ["shipment_ref", "ship_date", "freight_cost"], kind="mergesort")  # urutan pasti

    dup = ok.duplicated(subset="shipment_ref", keep="first")
    rejects = pd.concat([rejects, ok[dup].assign(reject_reason="DUPLICATE_REF")])
    clean = ok[~dup]
    return clean, rejects

def reconcile(raw: pd.DataFrame, clean: pd.DataFrame, rejects: pd.DataFrame):
    # 1) setiap baris input harus berakhir di clean ATAU rejects
    assert len(raw) == len(clean) + len(rejects), "Jumlah baris tidak cocok"
    # 2) total biaya input harus sama dengan total clean + rejects
    raw_cost = pd.to_numeric(raw["freight_cost"], errors="coerce").fillna(0).sum()
    out_cost = clean["freight_cost"].fillna(0).sum() + rejects["freight_cost"].fillna(0).sum()
    assert abs(raw_cost - out_cost) < 0.01, "Total biaya tidak cocok"
# load.py — idempotent: dijalankan dua kali hasilnya sama (upsert), dalam satu transaksi
SQL = """
INSERT INTO shipment (shipment_ref, carrier_id, origin, destination,
                      ship_date, promised_date, delivered_date, weight_kg, freight_cost)
SELECT %s, c.carrier_id, %s, %s, %s, %s, %s, %s, %s
FROM carrier c WHERE c.carrier_code = %s
ON CONFLICT (shipment_ref) DO UPDATE SET
  carrier_id = EXCLUDED.carrier_id, origin = EXCLUDED.origin, destination = EXCLUDED.destination,
  ship_date = EXCLUDED.ship_date, promised_date = EXCLUDED.promised_date,
  delivered_date = EXCLUDED.delivered_date, weight_kg = EXCLUDED.weight_kg,
  freight_cost = EXCLUDED.freight_cost
"""

def load(clean, conn):
    rows = [(r.shipment_ref, r.origin, r.destination, r.ship_date.date(), r.promised_date.date(),
             None if pd.isna(r.delivered_date) else r.delivered_date.date(),
             float(r.weight_kg), float(r.freight_cost), r.carrier_code)
            for r in clean.itertuples()]
    with conn.transaction():                 # semua berhasil, atau tidak sama sekali
        with conn.cursor() as cur:
            cur.executemany(SQL, rows)
            # cek pasca-load: carrier tak dikenal membuat SELECT di atas menghasilkan 0 baris
            # (baris hilang diam-diam!). Pastikan semua resi benar-benar ada di tabel.
            cur.execute("SELECT COUNT(*) FROM shipment WHERE shipment_ref = ANY(%s)",
                        (list(clean["shipment_ref"]),))
            assert cur.fetchone()[0] == len(clean), "Ada resi yang tidak ter-load (carrier tak dikenal?)"

Langkah 3 — Tes dari kasus yang disepakati

Mulai dari contoh nyata yang disetujui peminta (di sini: kasus-kasus kecil yang mewakili aturan bisnis), lalu jadikan tes.

# test_etl.py (jalankan: pytest -q)
import pandas as pd
from etl import transform, reconcile

COLS = ["shipment_ref","carrier_code","origin","destination",
        "ship_date","promised_date","delivered_date","weight_kg","freight_cost"]

def make(rows):
    return pd.DataFrame(rows, columns=COLS)

RAW = make([
    [" sh-001 ", "jne ", "JKT", "SBY", "2025-03-01", "2025-03-04", "2025-03-03", "12.5", "150000"],  # valid, perlu dirapikan
    ["SH-002",   "JNE",  "JKT", "BDG", "2025-03-01", "2025-03-03", None,         "0",    "90000"],   # berat 0
    ["SH-003",   "SICEPAT","JKT","MDN", "2025-03-01", "2025-02-27", None,         "5",    "70000"],   # janji sebelum kirim
    ["SH-001",   "JNE",  "JKT", "SBY", "2025-03-01", "2025-03-04", "2025-03-03", "12.5", "150000"],  # duplikat resi
])

def test_known_cases():
    clean, rejects = transform(RAW)
    assert list(clean["shipment_ref"]) == ["SH-001"]
    assert list(clean["carrier_code"]) == ["JNE"]
    assert sorted(rejects["reject_reason"]) == [
        "BAD_PROMISED_DATE", "DUPLICATE_REF", "INVALID_WEIGHT"]

def test_reconciliation_holds():
    clean, rejects = transform(RAW)
    reconcile(RAW, clean, rejects)           # tidak boleh melempar error

def test_deterministic():
    a, _ = transform(RAW)
    b, _ = transform(RAW.sample(frac=1, random_state=1))   # urutan input diacak
    assert a.reset_index(drop=True).equals(b.reset_index(drop=True))
Kenapa tes ketiga penting? Itu bukti "deterministic" yang tertulis di lowongan. Jangan lupa jalankan tesnya sendiri dan perbaiki bila ada yang gagal; kode di sini adalah kerangka untuk dipelajari, bukan sesuatu yang boleh dipercaya tanpa dijalankan.

Langkah 4 — Web tool untuk mencatat kendala (validasi + audit trail)

# app.py (FastAPI) — kerangka; autentikasi di dunia nyata pakai SSO perusahaan, bukan header
from typing import Literal, Optional
from fastapi import FastAPI, Header, HTTPException
from pydantic import BaseModel, Field
import psycopg
from psycopg import errors

app = FastAPI()
Category = Literal["DAMAGED", "DELAYED", "LOST", "WRONG_ADDRESS", "REFUSED", "OTHER"]

class ExceptionIn(BaseModel):
    shipment_ref: str = Field(min_length=3, max_length=40)
    category: Category                                  # hanya nilai baku
    note: Optional[str] = Field(default=None, max_length=500)

@app.post("/exceptions", status_code=201)
def create_exception(body: ExceptionIn, x_user: str = Header(...)):
    ref = body.shipment_ref.strip().upper()
    with psycopg.connect(DSN) as conn:                  # satu transaksi; rollback bila error
        with conn.cursor() as cur:
            cur.execute("SELECT set_config('app.user', %s, true)", (x_user,))  # untuk audit trigger
            cur.execute("SELECT shipment_id FROM shipment WHERE shipment_ref = %s", (ref,))
            row = cur.fetchone()
            if row is None:
                raise HTTPException(404, f"Resi {ref} tidak ditemukan")
            try:
                cur.execute(
                    "INSERT INTO delivery_exception (shipment_id, category, note, reported_by) "
                    "VALUES (%s, %s, %s, %s) RETURNING exception_id",
                    (row[0], body.category, body.note, x_user))
            except errors.UniqueViolation:
                raise HTTPException(409, "Kendala OPEN untuk resi dan kategori ini sudah ada")
            return {"exception_id": cur.fetchone()[0]}

Hal yang membedakan tool "jalan" dengan tool "bisa dipercaya": pesan error yang jelas untuk pengguna non-teknis, validasi di dua lapis (aplikasi dan database), dan jejak audit yang otomatis dari trigger sehingga nggak bergantung pada kode aplikasi.

Langkah 5 — Dashboard performa carrier

-- v_carrier_performance: on-time %, lead time, biaya per kg, dan rasio kendala per bulan
CREATE VIEW v_carrier_performance AS
SELECT c.carrier_name,
       DATE_TRUNC('month', s.ship_date)::date AS bulan,
       COUNT(*)                                            AS total_kirim,
       COUNT(*) FILTER (WHERE s.delivered_date IS NOT NULL) AS terkirim,
       ROUND(100.0 * COUNT(*) FILTER (WHERE s.delivered_date <= s.promised_date)
             / NULLIF(COUNT(*) FILTER (WHERE s.delivered_date IS NOT NULL), 0), 1) AS on_time_pct,
       ROUND(AVG(s.delivered_date - s.ship_date)
             FILTER (WHERE s.delivered_date IS NOT NULL), 1)  AS avg_lead_days,
       ROUND(SUM(s.freight_cost) / NULLIF(SUM(s.weight_kg), 0)) AS biaya_per_kg,
       ROUND(100.0 * COUNT(DISTINCT e.shipment_id) / COUNT(*), 1) AS pct_ada_kendala
FROM shipment s
JOIN carrier c            ON c.carrier_id = s.carrier_id
LEFT JOIN delivery_exception e ON e.shipment_id = s.shipment_id
GROUP BY c.carrier_name, DATE_TRUNC('month', s.ship_date);
Dokumentasikan definisinya On-time % di atas memakai penyebut "sudah terkirim". Pengiriman yang belum tiba tidak dihitung, dan itu bisa membuat angka terlihat terlalu bagus. Tulis definisi ini di dashboard dan konfirmasi dengan tim logistik, atau sediakan versi alternatif yang memperlakukan pengiriman lewat tenggat tapi belum tiba sebagai terlambat.

4Workflow AI & Penilaian atas Kode AI

Dua topik yang pasti dibahas: membangun alur kerja berbasis AI yang aman, dan bertanggung jawab atas kode yang dibantu AI.

Contoh: mengelompokkan catatan bebas kendala dengan guardrail

Catatan seperti "paket penyok kena hujan, penerima nolak" harus dipetakan ke kategori baku. AI membantu, tapi hasilnya diperiksa berlapis; kalau ragu, diarahkan ke manusia.

# classify.py — call_llm adalah fungsi yang lo sediakan (API model apa pun); di tes diganti stub
import json

ALLOWED = ["DAMAGED", "DELAYED", "LOST", "WRONG_ADDRESS", "REFUSED", "OTHER"]
PROMPT = ("Klasifikasikan catatan kendala pengiriman ke SATU kategori dari: {cats}. "
          'Balas HANYA JSON: {{"category": "...", "confidence": 0.0}}. Catatan: {note}')

KEYWORDS = {
    "LOST":          ["hilang", "lost"],
    "DAMAGED":       ["rusak", "penyok", "pecah", "basah"],
    "DELAYED":       ["telat", "terlambat", "macet"],
    "REFUSED":       ["tolak", "menolak"],
    "WRONG_ADDRESS": ["alamat salah", "alamat tidak ditemukan"],
}

def rule_based(note: str):
    n = note.lower()
    for cat, words in KEYWORDS.items():
        if any(w in n for w in words):
            return cat
    return None

def review(reason): return {"category": "NEEDS_REVIEW", "reason": reason}

def classify(note: str, call_llm, threshold: float = 0.7):
    try:
        out = json.loads(call_llm(PROMPT.format(cats=", ".join(ALLOWED), note=note)))
        cat, conf = out["category"], float(out["confidence"])
        assert cat in ALLOWED and 0 <= conf <= 1
    except Exception:
        return review("output AI tidak valid")           # lapis 1: format & nilai harus sah
    if conf < threshold:
        return review("confidence rendah")               # lapis 2: ambang keyakinan
    rule = rule_based(note)
    if rule and rule != cat:
        return review(f"AI={cat} tidak sesuai aturan={rule}")  # lapis 3: cross-check independen
    return {"category": cat, "confidence": conf, "reason": "ok"}
Lapis pengamanMencegah apa
Validasi format & daftar nilai bakuOutput ngawur, kategori karangan, JSON rusak
Ambang keyakinanTebakan lemah masuk ke laporan
Cross-check dengan aturan sederhanaKesalahan yang terdengar meyakinkan tapi bertentangan dengan teks
Jalur NEEDS_REVIEW ke manusiaKeputusan penting diambil tanpa pengawasan
Log prompt, output, keputusan akhirTidak bisa ditelusuri saat ada keluhan
Evaluasi berkala pada data berlabelKualitas menurun tanpa disadari (data atau model berubah)

Evaluasi: label manual 100–200 catatan sebagai "kunci jawaban", jalankan classify, lalu laporkan akurasi pada yang diproses otomatis, persentase yang dilempar ke review, dan contoh kesalahan terbesar. Ubah ambang berdasarkan hasilnya, bukan perasaan. Jangan sembunyikan angka yang jelek; itu justru menunjukkan kematangan.

Kapan AI tidak cocok? Kalau ada aturan deterministik yang cukup (misalnya mencocokkan kode carrier ke daftar baku), pakai aturan. AI untuk teks bebas dan pola yang sulit ditulis sebagai aturan. Alasan memilih "tidak pakai AI" kadang justru jawaban terbaik di interview.

Tulis query: 3 carrier dengan persentase keterlambatan tertinggi bulan lalu. Live coding
Maksudnya

Kemungkinan ada tes langsung. Mereka melihat cara berpikir, bukan hanya hasil.

Contoh jawaban 
SELECT c.carrier_name,
       COUNT(*) AS terkirim,
       ROUND(100.0 * COUNT(*) FILTER (WHERE s.delivered_date > s.promised_date) / COUNT(*), 1) AS late_pct
FROM shipment s
JOIN carrier c ON c.carrier_id = s.carrier_id
WHERE s.delivered_date IS NOT NULL
  AND s.ship_date >= DATE_TRUNC('month', CURRENT_DATE) - INTERVAL '1 month'
  AND s.ship_date <  DATE_TRUNC('month', CURRENT_DATE)
GROUP BY c.carrier_name
HAVING COUNT(*) >= 30           -- abaikan carrier dengan sampel kecil
ORDER BY late_pct DESC
LIMIT 3;

Sambil menulis, ucapkan asumsinya: "Saya hitung hanya yang sudah terkirim, dan saya pakai minimum 30 pengiriman supaya persentasenya tidak menipu."

C. Teknis: Python, ETL, tes, Git

Apa arti ETL yang "deterministic" dan "verifiable"? Bagaimana memastikannya? ETL
Maksudnya

Frasa dari lowongan, hampir pasti ditanya.

Contoh jawaban

"Deterministic: input yang sama selalu menghasilkan output sama. Saya pastikan dengan tidak memakai nilai acak atau waktu sekarang di dalam transformasi, mengurutkan secara eksplisit sebelum deduplikasi, dan menulis tes yang mengacak urutan input lalu membandingkan hasilnya. Verifiable: ada rekonsiliasi, yaitu jumlah baris input sama dengan clean ditambah reject, total nilai cocok dengan sumber, dan setiap baris yang ditolak punya alasan tertulis. Hasil rekonsiliasi disimpan sebagai log."

Maksudnya

"Idempotent artinya dijalankan sekali atau berkali-kali hasil akhirnya sama. Caranya pakai upsert (INSERT ... ON CONFLICT DO UPDATE) pada kunci bisnis dan transaksi. Tanpa itu, menjalankan ulang job menghasilkan duplikat atau data setengah masuk."

Maksudnya

Contoh jawaban 
def dedupe_latest(df):
    df = df.sort_values(["shipment_ref", "updated_at"], kind="mergesort")
    dup = df.duplicated("shipment_ref", keep="last")
    removed = df[dup]                     # simpan untuk jejak, jangan buang diam-diam
    return df[~dup], removed

Risikonya: "terbaru" harus didefinisikan jelas (kolom apa?), dan baris yang dibuang harus dicatat agar bisa diaudit.
